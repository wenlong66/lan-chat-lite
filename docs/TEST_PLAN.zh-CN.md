# LanChat Lite 测试与验收计划

## 1. 什么证据能证明什么

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| 源码检查 | 生命周期、边界和协议的实现意图 | 程序已运行成功、实际内存或速度 |
| 本机 QtTest / loopback | 受测逻辑、真实本地 socket 的边界行为 | 跨系统、Wi-Fi、防火墙、睡眠恢复表现 |
| GitHub Actions 绿色 | 对应提交在指定系统上构建、测试、打包通过 | 用户两台电脑已互传、网络满速 |
| 实体 Windows ↔ Mac 测试 | 指定硬件和网络条件下的双向表现 | 所有硬件、所有路由器的性能保证 |

**本文是一份计划，不是通过报告。** 实际通过项须在测试记录中附命令输出或可复核结果；未执行项写“待测”。首版状态以仓库 README/测试结果记录及相应提交的 Actions 为准。

## 2. 自动回归门槛

每次更改协议、文件读写或图片输入后执行 Release 构建和全部 CTest：

```bash
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure --no-tests=error --timeout 90
```

无桌面的 Linux 加 `QT_QPA_PLATFORM=offscreen`。本地网络测试需要允许 loopback socket；沙箱若禁止 socket，记录为环境阻止，不算测试通过。

关注：零字节文件、恰好一个分块、分块加一字节、多分块、双方完成确认、接收拒绝、慢接收、连接断开、重复传输资源释放、图片粘贴 MIME 数据。测试名称和覆盖率以 `ctest --test-dir build -N` 与实际测试文件为准，不按文档推断已覆盖。

继承的 `tests/robot` 和 `tools/lmm` 有旧协议 mock。Lite 文件握手变更后，旧 mock 的文件互传用例不能直接当本版验收依据。首版 CI 不运行这套未适配的 mock 文件测试；后续应升级 mock 后再扩展 GUI 全链路覆盖。

## 3. 实体机基本功能（两个方向都做）

| 用例 | 操作与通过标准 |
|---|---|
| 设备发现 | 冷启动两端，能看见对方且昵称正确；记录发现时间 |
| 中文和 emoji | 各发多行中文、英文、链接、emoji，顺序和内容一致 |
| 界面语言 | 无语言设置时简体中文系统加载中文；首选项切换简体中文/English 后立即生效且重启保留；检查菜单、聊天、截图错误、传输进度和标准取消按钮，缺失或不支持的语言包回退英文；Windows/macOS 分别检查中文排版 |
| 连续聊天 | 双方各发 100 条，检查丢失、重复、窗口响应 |
| 剪贴板图片 | Windows/Mac 各截一张图粘贴，确认预览发送；接收 PNG 可正常打开，取消预览不得发送 |
| 普通文件 | 拖拽和按钮选择都可发送；接收端接受后大小与 SHA-256 一致 |
| 拒收 | 接收端拒绝，无成功提示、无残留完整文件 |
| 同名文件 | 先后及并发接收同名不同内容文件，分别保存为 `文件名.ext`、`文件名_1.ext`、`文件名_2.ext`；覆盖无扩展名、中文名及大小写差异，逐一核对内容不被覆盖 |
| 图标临时文件 | 在独立测试环境的临时目录预置同名哨兵文件，再创建尚未落盘的附件图标；哨兵内容不变，应用独立图标临时目录用后清理 |
| 无分组联系人 | 精简版联系人平铺，添加、离线、改名及联系人选择正常；分组入口不可用，重复启动不迁移或覆盖已有分组文件 |
| 特殊文件名 | 中文、空格、emoji、长文件名分别测试；路径合法且内容不变 |
| 托盘常驻 | 关闭主窗口后仍能接收提醒，退出后不残留进程 |

请两端使用同一提交的 Lite。原版 LAN Messenger 混用时文件兼容性不在首版承诺范围。

## 4. 文件完整性与异常

测试文件组建议：**0 B、1 B、65,535 B、65,536 B、1 MiB、32 MiB、1 GiB、10 GiB**，再补 1,000 个小文件。测试数据单独放在临时目录；不用真实私密文件，也不把大文件提交到仓库。

Windows 哈希：

```powershell
Get-FileHash 'C:/lan-chat-test/sample.bin' -Algorithm SHA256
```

macOS/Linux 哈希：

```bash
shasum -a 256 /path/to/lan-chat-test/sample.bin
```

哈希一致是内容正确性的验收条件；“进度条 100%”或“大小相同”都不足以替代。

异常测试：

1. 在 10 GiB 文件中途断开网络，确认双方不会误报成功；恢复网络后可重新发送。当前不支持断点续传。
2. 发送端与接收端分别取消，确认任务终止、未完成数据按实现清理、其他聊天可继续。
3. 使用独立的小容量测试卷或配额模拟接收空间不足，不要填满工作系统盘；确认失败提示明确且无“完成”。
4. 发送过程中退出一端、让一端睡眠再唤醒，检查对方超时与后续重发。
5. 缩小接收速度或用低速测试盘，检查应用内存不会因待写数据无限堆积。
6. 在专用测试副本上测试“传输途中源文件被修改/截短”，记录是否检测到变化。当前的流式摘要保证接收内容与实际发送的字节流一致，不等于为源文件创建稳定快照；不要用仍在写入的文件做正常完整性与测速样本。

## 5. 速度测试

先记录：两端系统/CPU/内存/SSD型号、网卡速率、是否网线、交换机/路由器、Wi-Fi频段与信号情况、应用提交 SHA、Qt版本、加密设置。关闭不相关的大流量任务。

用同一份 **5–10 GiB 已存在的不可压缩文件**，Windows→Mac、Mac→Windows 各做三次。计时从接收端接受到双方确认完成，哈希计算在计时结束后进行。记录三次数据和中位数，不只挑最快一次。另测 1,000 个小文件，总耗时单列，不与大文件吞吐混用。

公式：`MB/s = 文件字节数 ÷ 1,000,000 ÷ 秒数`。MiB/s 使用 `1,048,576` 分母，报告中勿混淆。单次文件哈希不一致时，该次速度无效。

**目标：千兆有线、两端 SSD 且链路无明显瓶颈时，大文件中位速度达到 80 MB/s 以上。** 这是设计目标，尚不能当成产品实测结果。1 Gbit/s 的裸换算上限是 125 MB/s，实际需扣协议开销。Wi-Fi 不预设绝对速度承诺，应先测本地 TCP 基线，再定位软件开销。

可使用 [iperf](https://software.es.net/iperf/) 测网络基线；Windows 构建应从可信来源取得，ESnet 本身没有正式支持 Windows。测试网络基线不能代替真实文件与磁盘路径的测试。

## 6. 内存、资源与 24 小时常驻

在 Release 构建中采样四个阶段：启动后空闲 5 分钟；托盘常驻；打开聊天并连续传图；完成 1,000 个文件后再空闲 5 分钟。分别记录基线、中位、峰值、结束值和进程数。

Python 3 标准库采样脚本：

```bash
python scripts/sample_memory.py --pid 12345 --duration 1800 --interval 2 --out memory-30min.csv
python scripts/sample_memory.py --pid 12345 --duration 86400 --interval 30 --out memory-24h.csv
```

将 `12345` 换成应用真实 PID。脚本用本机 PID、父 PID 与内存元数据定位进程树，只把指定应用及其子进程的汇总值写入 CSV；不读取消息内容、用户文件或环境变量，也不会改变进程。输出路径必须不存在，避免覆盖旧记录。退出应用后脚本停止；Ctrl+C 可提前停止并保存已有记录。

Windows 指标是 working set，macOS/Linux 是 RSS；进程树求和可能重复计算共享页，所以应在同一系统、同一测量口径下看趋势，不能把三个系统的数字直接当成严格的物理内存排名。用任务管理器/活动监视器复核。安装包大小不算运行内存。

**初步目标**：托盘常驻约 50 MB；大文件传输中内存不随累计已传字节线性增长；批量任务结束后接近基线；24小时内没有持续增长、崩溃或失联。图片解码与系统缓存可产生瞬时峰值，是否泄漏需结合传输结束后的趋势和对象/句柄统计判断。

在 Linux 开发机另做 AddressSanitizer/LeakSanitizer 验证网络回归，有助于区分内存泄漏与缓存；它的内存/速度不能作为 Release 性能成绩。
