# LanChat Lite 开发路线

## 目标与首版范围

Windows＋macOS，同一局域网内的单聊、截图/图片附件和文件直传。先验证小范围、可靠和资源可控，再优化界面与性能。基础代码来自 LAN Messenger v1.3.9，许可证与原作者署名继续保留。

首版为 **0.1.0-alpha**，有运行中的开发工作，不等同于已经完成实体 Windows↔Mac 验收的正式版。以提交中的代码、测试日志和 Actions 结果区分状态。

| 阶段 | 交付内容 | 进入下一阶段的依据 |
|---|---|---|
| P0：建立可构建的派生项目 | 来源与 GPL 说明；精简模式；修复传输生命周期与队列；Lite 文件完成确认；图片粘贴；CI 与测试文档 | 对应提交的自动测试与目标平台构建通过 |
| P1：两台电脑验收 | Windows↔Mac 双向文字/图片/文件；取消/断线/重发；文件哈希；记录系统权限与启动表现 | 实体机测试记录完整，不把 loopback 替代为跨系统通过 |
| P2：资源与速度 | 千兆有线大文件、千个小文件、重复传图；内存/句柄/临时文件；24h常驻 | 有可复核数据、无持续增长；性能达到约定目标或记录明确瓶颈 |
| P3：个人日常测试版 | 修复 P1/P2 问题；完善双端包；精简设置与提示 | 本人能稳定日常使用，已知限制可接受 |

### 首版协议决策

文件路径采用 `START2\n` / `DONE2 <SHA-256>\n` 握手，接收端成功提交临时文件、发回摘要后，发送端比对流式 SHA-256，再报告完成。传输采用 64 KiB 分块，每连接 Qt 队列限制为 512 KiB，30 秒无进展超时。多个连接的合计内存仍需测量，不能把单连接队列上限当作进程总内存。

首版文件互传范围是 **Lite↔Lite**，不承诺与上游原版文件互通。发现和文字仍沿用上游协议。

当前文件传输未加密、没有断点续传；SHA-256 回执用于传输一致性核对，不提供端点身份认证或恶意篡改保护。首次测试只在可信局域网进行。完善端点身份校验与文件加密应作为后续独立变更，有新的协议版本与回归覆盖，不能把“已有文字加密”写成“文件全程加密”。

### 后续按实际问题选择

- 如果大量文件后内存/句柄仍增长，先修生命周期与缓存上限。
- 如果大文件吞吐低于同网段基线，定位磁盘、队列、线程与系统调用；先有测量，再调整并发。
- 如果经常传很大的文件且网络容易中断，再增加有校验的断点续传。
- 已补截图自动接收与聊天内缩略图（320×240、8 MiB 共享缓存）；下一步按实体 Windows↔Mac 双向传图验证，完整历史图库和图片编辑不在本轮范围。
- 如果频繁误认设备，再加入本地信任设备与首次配对确认，并同时处理文件加密。
- 如果需要向更多用户分发，再单独处理 Windows 签名和 Mac Developer ID 公证。

## Codex 每轮执行方式

1. 阅读根 README、`docs/GETTING_STARTED.zh-CN.md`、`docs/TEST_PLAN.zh-CN.md`，确认当前提交和待完成项。
2. 每轮只完成一个明确问题；先写复现步骤，再修改对应代码。
3. 协议和资源管理改动增加能触及失败路径的回归测试，不只测试正常发送。
4. 编译并跑全部 CTest；检查目标平台 Actions。遇到环境限制写明限制，不伪造通过。
5. 需要 Windows↔Mac 实机才能判断的行为，记录待测步骤，让实体机测试结果回到仓库。
6. 更新结果记录、已知限制与下一项任务，再提交代码。

可直接交给 Codex 的下一轮任务：

> 读取本项目文档，先确认当前分支全部 CTest 与 Windows/macOS CI 结果。根据 TEST_PLAN 的基本功能和文件完整性用例逐项复核。若只能在 Linux/单机环境执行，仅报告已执行范围，保留 Windows↔Mac 待测项。优先修复会导致内容损坏、误报完成、内存或句柄持续增长的问题；保持精简功能范围；完成后更新测试记录并提交。

首版不会主动引入云账号、云中转、群聊扩展或远程控制。新增功能须对局域网聊天、传图或文件可靠性有直接帮助。
